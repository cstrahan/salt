Derive minion presence from publish-channel subscriptions on the zeromq
transport. Presence was decided by matching each minion's *cached grain*
ipv4 / ipv6 against the addresses connected to the publish port, so a minion
connecting from a different address than its grains report -- NAT, floating
IPs, a master managing minions in another network -- was reported absent
while being perfectly reachable. Subscribers now announce their identity to
the publish server when they connect, and ``CkMinions.connected_ids()``
takes that into account, so the fix reaches ``manage.present``,
``manage.not_present``, ``manage.list_state``, ``manage.alived``, the
``minions.connected`` wheel, ``max_minions`` enforcement and
``ping_all_connected_minions`` alike -- on the tcp transport too, which was
equally unable to see a NAT'd minion.

The publish server's record is *unioned* with the existing address
matching rather than replacing it: the record names the minion behind a
connection, which address matching cannot do under NAT, while address
matching still sees connections the record cannot name -- minions too old
to announce themselves. For any minion the record names, the record wins,
so the address reported is the real one. A partly-upgraded fleet therefore
reports every minion either mechanism can see, and the answer can only be
a superset of what Salt reported before.

This fixes minions wrongly reported **absent**. It does not make the
cached-grain heuristic reliable in the other direction: a minion that has
gone away but whose stale grain address still matches some other
connection is still reported present, exactly as before.

On zeromq this is opt-in through the new ``zmq_presence_subscriptions``
master option; see its entry in the master configuration reference for the
caveats. The chief one is that it needs minions new enough to announce
themselves -- older ones are covered only by address matching, as before,
and the ``salt/presence/*`` event stream names only minions that announce.

**On the tcp transport there is nothing to enable and no way to opt out**:
that transport authenticates its publish connections, so the master has
always known which minion each one is, and ``connected_ids()`` now uses it.
A tcp master therefore picks up the consequences below on upgrade, with no
configuration change.

Worth calling out:

- ``max_minions`` is enforced against a count that can only grow, never
  shrink, relative to before -- so the limit can fail closed where it
  previously failed open, but not the reverse. A fleet quietly over its
  limit will start seeing authentication rejections. Syndics count too.
  Audit your headroom before upgrading a tcp master, where this is not
  opt-in. With ``con_cache`` enabled the change reaches enforcement only
  at that cache's update interval.
- ``manage.present show_ip=True`` and anything else reading
  ``connected_ids(show_ip=True)`` now reports the address the minion is
  connected *from*, for any minion the publish server can name, rather
  than the cached grain address that happened to match. For a NAT'd fleet
  those differ. Where the transport cannot report an address at all, such
  as zeromq over IPC, the record carries an empty string and whatever
  address matching found is used instead.
- An upgraded minion announces itself whatever the master is configured to
  do, so it now puts one extra subscription on the wire. It carries no
  identifier an observer can read -- the topic is an opaque digest the
  master assigns, with no relationship to the minion's id -- but it is
  one more topic in ZeroMQ's subscription trie.

Each master answers for the minions connected to it, which is the scope
address matching always had; Salt does not merge presence across a cluster.
``zmq_filtering`` is unrelated and does not enable any of this.
